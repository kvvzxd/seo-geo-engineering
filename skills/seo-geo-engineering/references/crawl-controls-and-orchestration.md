# crawl-controls-and-orchestration

## Управление поисковыми политиками и оркестрация скриптами

Используй этот справочник при изменении правил доступа. Реализованные команды и границы автоматизации: [tool-contracts.md](tool-contracts.md).

#### 23.1. Разделение уровней управления

Агент должен уметь создавать, изменять и согласовывать:

1. **Обход**: `robots.txt`, `User-agent`, `Allow`, `Disallow`, ссылки на sitemap, поддерживаемые расширения конкретного робота.
2. **Индексирование**: HTML robots meta и HTTP `X-Robots-Tag`, в том числе для PDF и других ресурсов.
3. **Представление содержания**: применимые `nosnippet`, `max-snippet`, `max-image-preview`, `max-video-preview`, `data-nosnippet` и другие документированные средства.
4. **Обнаружение изменений**: sitemap, RSS/Atom, достоверные даты и уведомления IndexNow для участвующих систем.
5. **Фактический сетевой доступ**: маршрутизация, CDN/WAF, доступность ресурсов рендера, проверка принадлежности робота и разумные ограничения нагрузки.
6. **Доступ для генеративного поиска, обучения и пользовательского получения**: отдельные настройки по документированным ролям.
7. **Дополнительные машинные представления**: `llms.txt`, актуальные Markdown-версии и публичные структурированные данные, когда есть конкретный полезный сценарий.
8. **Внутреннюю оркестрацию**: конфигурацию, граф зависимостей, планировщик или CI-проверки, которые поддерживают перечисленные уровни в согласованном состоянии.

Эти механизмы имеют разные полномочия. Robots не управляет исполнением скриптов агента и не задаёт генеративной системе порядок рекомендаций. Внутренний manifest оркестрации исполняется собственными инструментами скилла; внешние поисковики не обязаны его читать. Указывай, где правило реально действует и кто его поддерживает.

#### 23.2. Конфигурация как источник согласованных правил

Используй локальный manifest. Концептуальная модель ниже показывает намерения, а фактически исполняемый JSON-контракт и пример находятся в [tool-contracts.md](tool-contracts.md). Это внутренняя схема скилла, не отраслевой стандарт. Расширяй её только при необходимости задачи, реализуя и проверяя адаптер. Раздели намерение владельца и способ его реализации для конкретной платформы.

Схематический пример:

```yaml
schema_version: 1
environment: production
origins:
  - https://example.com
preserve_unmanaged_rules: true
unknown_capability: report_and_skip
bot_intent:
  search: preserve_existing_then_optimize
  training: preserve_owner_choice
  user_fetch: preserve_owner_choice
route_sets:
  public_services:
    paths: [/services/, /prices/]
    desired:
      crawl: allow
      index: eligible
      preserve_offer_conditions: true
  account_area:
    paths: [/account/]
    desired:
      access: authenticated
      search_visibility: exclude
      crawler_mechanism: determine_from_current_state
discovery:
  sitemap: https://example.com/sitemap.xml
  truthful_lastmod: true
  indexnow:
    enabled: false
    enable_only_when_configured_and_authorized: true
machine_views:
  llms_txt:
    enabled: false
    requires_identified_consumer_or_use_case: true
  markdown:
    enabled: false
    synchronize_protected_facts: true
critical_examples:
  - url: https://example.com/services/
    crawler_profile: google_search
    expected_crawl: allow
    expected_indexing_directive: no_blocking_directive
    expected_offer_conditions: preserved
release:
  default: plan
  apply_within_existing_authorization: true
  compare_current_version_before_write: true
  post_publish_verify: true
```

Это не готовая конфигурация пользователя. Не публикуй `example.com`, фиктивные пути или неподтверждённые намерения. Значение `eligible` означает отсутствие известных запретов, а не гарантию включения в индекс. Наличие закрытого account-раздела не означает, что можно безопасно решить приватность одним noindex.

Применимые robots-группы и поддерживаемые директивы выбирает проверяемый адаптер системы. Не превращай собственные поля manifest в выдуманные строки robots.txt. По умолчанию сохраняй действующий выбор владельца по обучению моделей и пользовательскому доступу.

#### 23.3. Генерация и проверка robots.txt

Используй [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309) и действующую документацию робота. Реализуй получение и разбор существующего файла, построение эффективных разрешений, минимальный обоснованный diff и проверку на наборе реальных URL. Учитывай область origin, UTF-8, регистр путей, кодирование URL и сопоставление правил. Не используй собственный regex как полную реализацию протокола без проверки на репрезентативных случаях.

Для Google обязательно учитывай, что специфическая группа User-agent не наследует автоматически ограничения `*`; проверь объединение групп одного агента, специфичность путей и разрешение совпадений по документированной семантике. Не полагайся на порядок строк как на универсальный приоритет. Проверяй ограничения размера, HTTP-ошибки получения, редиректы и кэширование. [Спецификация Google](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec)

Сохраняй доступ к CSS, JS и другим ресурсам, необходимым для корректного рендера индексируемых страниц. Не закрывай все URL с `?`, все JSON или все API без анализа: часть из них может содержать необходимые данные. Не генерируй глобальный `Disallow: /` как стандартный шаблон рабочего сайта. [Создание robots.txt](https://developers.google.com/crawling/docs/robots-txt/create-robots-txt)

Если целевая система поддерживает расширение, например Яндекс `Clean-param`, используй его только для параметров, которые не меняют значимое содержание, и проверь различающиеся примеры. Не удаляй как «трекинг» параметры товара, локали, варианта или тарифного расчёта. Поддержка расширения одним роботом не делает его общей нормой. [Clean-param](https://yandex.ru/support/webmaster/ru/robot-workings/clean-param)

Перед публикацией выведи матрицу `origin × URL × robot_profile → разрешение и объяснение`. Для запрета укажи сработавшую группу и правило; для неизвестной семантики верни `unknown`, а не произвольное `allow`.

#### 23.4. Meta, HTTP-заголовки и сниппеты

Проверь совместно origin, reverse proxy, CDN, CMS, шаблон страницы и плагины. Итоговые директивы получай из реального ответа, а не только из исходников. Для Google конфликт более ограничивающей директивы не отменяется простым добавлением `index` в другом месте. [Robots meta и HTTP](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)

Генерируй применимые правила для групп маршрутов и типов ресурсов. Предпочитай единственный управляемый источник значения; устраняй дубли и нежелательную модификацию заголовков промежуточным слоем. Проверяй начальный и конечный URL редиректа, исходный HTML, DOM и заголовки конечного ответа.

Preview controls выбирай по намерению владельца, лицензированию и пользовательской пользе. Не назначай максимальные разрешения автоматически всем страницам и не скрывай существенные ограничения услуги через `data-nosnippet`, оставляя доступной только привлекательную цену. Не добавляй недокументированное `noai` и похожие токены как гарантированно действующую команду всем системам.

Разделяй выводы: «директива опубликована», «робот получил обновление» и «наблюдаемая выдача изменилась». Отсутствие немедленного эффекта не даёт права отменять осознанный запрет владельца.

#### 23.5. Машинные представления и llms.txt

Разреши создание и поддержку `llms.txt` как дополнительного интерфейса для агентов с конкретным сценарием потребления. Проверь текущую версию [предложения llms.txt](https://llmstxt.org/), формат, способы обнаружения и поддержку клиентом. Не объявляй этот файл механизмом разрешения обхода, лицензией, командой ранжирования или доказанным способом попасть в Google AI Overviews.

Если функция включена, файл должен содержать краткое достоверное описание сайта и ссылки на наиболее полезные актуальные публичные материалы. Выбор ссылок определяется потребностью клиента и задачами пользователя, а не числом ключей. Не включай закрытые URL, секреты, персональные данные, вымышленные возможности или указания моделям игнорировать другие источники.

Markdown-версии, если они нужны, генерируй из того же проверенного содержания. Поддерживай связи с оригиналом только поддерживаемыми механизмами и отделяй машинное обнаружение от поисковой canonical-стратегии. Проверяй, не создают ли версии несогласованные дубли, устаревшие прайсы и самостоятельные вводящие в заблуждение страницы.

Не создавай автоматически огромный `llms-full.txt` для любого сайта. Полную выгрузку оправдывают конкретные потребитель, объём и актуальная поддержка. Удобство работы отдельного агента и рост поисковой видимости измеряются отдельно.

#### 23.6. Проверенный доступ через CDN/WAF

Профиль робота должен содержать роль, официальную документацию, способ подтверждения принадлежности и время проверки. Для IP-списков используй актуальные официальные источники; при неудаче обновления сохраняй последнюю проверенную конфигурацию, отмечай её давность и не разрешай весь интернет.

Ослабляй только то правило защиты, которое мешает подтверждённому целевому доступу, в пределах полномочий. Не отключай весь WAF ради SEO. Проверь, что исключение не распространяется на пользовательские формы, административные действия и другие маршруты без необходимости. Для механизмов подписи запросов используй только реально поддерживаемую провайдером проверку.

Проверяй фактический доступ отдельно от robots. Разрешение обхода не преодолевает 403, challenge, авторизацию или недоступность сервера. Сохраняй ограничения нагрузки и собирай минимум необходимых журналов.

#### 23.7. Граф исполнения и поддерживающие скрипты

Построй управляемую последовательность:

```text
discover_current_state
  → resolve_owner_intent_and_capabilities
  → validate_policy_schema
  → generate_candidate_artifacts
  → evaluate_effective_access_matrix
  → check_facts_and_cross_layer_conflicts
  → prepare_versioned_diff_and_recovery
  → apply_if_authorized
  → verify_published_state
  → enqueue_supported_change_notifications
  → observe_or_export_monitoring_plan
```

Генерация и применение — отдельные операции. Режим `plan` должен завершаться реальными кандидатами файлов/настроек и отчётом, не затрагивая рабочий сайт. При имеющемся разрешении на внедрение продолжай к `apply` после успешных проверок без повторного согласования каждого файла.

Для локальных файлов используй включённую CLI с командами `inspect`, `plan`, `validate`, `apply`, `verify`, `drift`, `rollback`. Возможности и ограничения указаны в tool-contracts. При необходимости проекта создавай и проверяй дополнительные адаптеры. Не делай генератор зависимым от доступа к платной SEO-платформе.

Требования к исполнению:

- одинаковые входы дают одинаковый результат; повторный запуск не создаёт лишние изменения;
- перед записью сравниваются текущая версия/хэш/ETag с подготовленным основанием;
- существующие неуправляемые правила сохраняются либо явно включаются в область переработки;
- незавершённая запись не оставляет усечённый robots.txt или повреждённую конфигурацию;
- зависимости выполняются по порядку, независимые чтения могут выполняться параллельно;
- сбои имеют ограниченные повторы, backoff и понятный статус; мутации не повторяются вслепую;
- уведомления отправляются после успешной публикации и проверки фактических изменений;
- staging и production имеют явные разные цели и защиту от переноса запретов;
- секреты не попадают в manifest, публичные файлы и журнал;
- откат восстанавливает конкретную версию управляемых настроек с учётом конкурентных правок.

Если весь пакет нельзя применить атомарно, используй этапы с проверкой состояния и компенсирующим восстановлением. Не заявляй транзакционность нескольких внешних сервисов, которой фактически нет.

#### 23.8. Автоматический контроль дрейфа

При запросе постоянного сопровождения поддержи проверки в доступном CI/планировщике либо подготовь пригодную к запуску конфигурацию. Не обещай, что мониторинг уже работает, если он не запущен.

Триггеры: изменение маршрутов/шаблонов, релиз CMS или плагина, обновление прайса, изменение robots/заголовков, новая локаль, изменение официального профиля бота. Проверяй критические URL после релиза и доступные агрегаты после переобхода.

Дрейф — расхождение намерения, сгенерированного артефакта и реально опубликованного состояния. Отчёт должен показать слой-источник, затронутые страницы и влияние. Новая блокировка ключевых услуг требует действия; неизменное штатное состояние не требует постоянных уведомлений. Автоисправление разрешено только в заранее установленной области; неизвестное изменение владельца не перезаписывается молча.

#### 23.9. Обязательные артефакты и критерии проверки

Для полноценной задачи управления политиками выдай:

- валидированный manifest с фактическими намерениями и областью действия;
- реестр профилей систем с источниками и ограничениями;
- текущие и предложенные robots/метатеги/HTTP-настройки и машинные файлы по применимости;
- понятный diff с объяснением, какие URL станут доступны или ограничены;
- матрицу эффективного доступа для критических и граничных URL;
- найденные конфликты обхода, индексирования, preview и WAF;
- журнал выполненных операций, реальную проверку опубликованного состояния и пакет восстановления;
- план сопровождения либо подтверждённую действующую автоматизацию, если это входило в задание.

При изменении оркестратора прогони связанные сценарии из [поведенческой матрицы](../evals/behavioral-scenarios.md). Разделяй синтаксический успех генератора, соответствие намерению владельца, доступ реального робота и фактическое изменение поисковой видимости. Одно не доказывает другое.
